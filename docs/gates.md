# 机器门禁:用检查取代信任

规则写在文档里,AI 会忘、会漏,人也审不完。门禁把规则变成「**不通过就进不去**」的硬约束——规模再大也不漏。

## 三道关卡:越往后越慢、越穷尽

快的挡低级错,慢的挡真问题。别把所有检查都堆在一处。

| 关卡 | 耗时 | 挡什么 | 放什么 |
|---|---|---|---|
| **① pre-commit** | 秒级 | 格式与低级错 | 暂存文件 lint 并自动修、空白符与结尾换行、依赖清单同步 |
| **② pre-push** | 分钟级 | 编译不过 | 全量类型检查;再按改动面挑**最小**检查集 |
| **③ CI** | 穷尽 | 真问题 | 逐文件覆盖率、快照、真实 API、多版本与多平台矩阵 |

任一道红 → 打回重做。

**关键纪律:pre-push 不跑全套。** 选恰好覆盖本次改动的最小集合,CI 才负责穷尽覆盖与平台矩阵。证据要对上改动面:行为改动 → 聚焦测试;用户/模型可见输出 → 快照;文档 → 文档门禁;发布路径 → 构建 + 产物冒烟。参考 [skills/dsh-pre-push-checks](../skills/dsh-pre-push-checks/SKILL.md)。

## 值得抄的门禁清单

```
□ 类型 / 编译零错误(严格模式)
□ 测试覆盖率(逐文件,而不是全局平均)
□ 文档死链检查(所有相对链接都能跳到)
□ 文档字数上限(防常驻规则文件膨胀)
□ 决策记录格式校验(骨架、必填节、状态与目录一致)
□ 跨文件重复代码检测
□ 提交信息规范 / 文件结尾恰好一个换行
□ 依赖与产物一致性(声明的依赖与实际引用相符)
□ 导出必须有文档注释
```

上游对应实现在 [deepseek-harness/scripts](https://github.com/deepseek-ai/deepseek-harness/tree/master/scripts),约 100 个 `verify-*` / `gen-*` 脚本可作参考。

## 两条最容易把门禁做废的地方

### 1. 加了门禁,但从没见它变红

一道从没失败过的门禁,可能是个**永远绿的摆设**——正则写错、路径不对、或者根本没被执行。

**做法:每加一道门禁,先故意制造一次违规,确认它真的报错,再修回来。** 上游把这条写进了审查要求:「一个 guard 只有在回归确实能让它失败时才算 guard」——引入回归、看它变红、再撤销。

### 2. 只在 prompt / schema 层「过滤」,当成了强制

这是最隐蔽的一种假安全:AI 写出「看起来限制住了、其实能绕过」的代码。

> **在做决策的那个操作里强制该决策。** schema 省略、prompt 过滤、facade、wrapper、listener 顺序都**不算**强制——直接调用或旁路调用能绕过它们。要在真正执行的那一层测到「拒绝」。

审查时的做法:顺着每条「拒绝」路径追到真正执行它的操作,然后用能绕过外层的调用方式去实测。

## 覆盖率门禁的反直觉用法

上游要求**逐文件 100%** 覆盖率,但它的态度值得抄:

> 一行没被覆盖,往往是门禁正确地标出了**该删的死代码**,而不是要给它补个测试。

于是同一道门禁,既逼你补测试、又逼你删废码。同时它明确承认边界:**行覆盖是必要条件,永远不是充分条件**——它只证明代码跑过了,不证明功能像发布时那样工作。

完整测试分层见 [docs/testing-policy.md](testing-policy.md)。

## 怎么起步

不要一上来铺 100 个脚本。顺序:

1. **类型检查**挂 pre-push —— 收益最大、成本最低。
2. 挑一条**你们团队反复犯**的格式/结构问题,写成脚本挂 pre-commit。
3. 加**决策记录格式校验** —— 它让机制②真正落地,否则记录会逐渐走形。
4. 覆盖率门禁进 CI —— 先设一个能过的门槛,再逐步收紧到逐文件。
5. 每加一道,都先制造一次违规验证它会红。

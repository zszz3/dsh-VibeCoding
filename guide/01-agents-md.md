# 一、常驻规则:AGENTS.md

## 为什么要这么做

你跟 AI 说「我们项目提交信息用中文、测试放 tests/ 目录」,它照做。第二天新开一个 session,它又用英文提交、把测试塞进了 src/。因为上一次对话它不记得。

每次重新交代一遍是可行的,但你交代的东西会漂:今天说得细一点、明天忘了说一条,不同的人交代的还不一样。

## dsh 怎么做

把规矩写进仓库里的 `AGENTS.md`。AI 每进一个 session 会自己读它,相当于每次开工前都递上同一份准则。

`CLAUDE.md` 是一个指向它的软链接:Claude Code 读前者,Codex 读后者,物理上是同一个文件。dsh 仓库的分支名里能同时看到 `codex/` 和 `worktree/` 前缀 —— 不同厂商的 AI 在同一个仓库里干活,读同一份规则,不需要维护两份再担心它们不一致。

## 里面写什么

[dsh 的根 AGENTS.md](../AGENTS.zh.md) 分九节。把它们按作用归一下,就是一份可以照着填的清单:

| 这一节 | 作用 | 具体写什么 |
|---|---|---|
| 开篇一两句 | 让 AI 知道自己在什么项目里 | 项目是什么、最重要的一条纪律、改核心代码前该先读哪份文档 |
| 目录布局 | 省掉 AI 到处翻找的时间 | 一棵注释过的目录树,每个顶层目录一行说明装什么 |
| 命令 | 让 AI 用对命令,而不是猜 | 一个代码块列常用命令,每条带注释;哪个是 CI 真正卡的门禁要写明 |
| 本地跑哪些检查 | 防止它每次跑全套或者干脆不跑 | 怎么按改动面选最小检查集,以及「只报告实际跑过的命令」 |
| 密钥 | 防止凭证进版本库 | 读哪些环境变量、放哪个文件、无 key 时的行为 |
| 代码约定 | 全篇的主体 | 每条一到三行的规则,后面挂链接 |
| AI 坏习惯自查 | 治那几种成体系的毛病 | 见[第四篇](04-bad-habits.md)的四条 |
| 类型安全与文档 | 什么时候必须写注释、写到什么程度 | 严格模式要求、导出必须有文档、注释写契约不写推理过程 |
| 怎么改这份说明 | 防止这个文件自己腐化 | 软链接改哪一份、字数上限怎么处理 |

前六节是骨架,后三节是让这套东西能长期活下去的。第一版可以只写开篇、命令、约定三节,其余等需要时再加。

## 每条规则怎么写

约定那一节是全篇主体,也是最容易写坏的地方。dsh 的写法有几个固定特征,拿一条真实的规则看:

> **Registrations are effects**: every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer.

拆开看:

- **加粗的结论放在最前面。** AI 扫一眼就知道这条讲什么,不用读完整句。
- **一到三行说完。** 这条只有一行,包含了做法(走 `ctx.effect()`)和一个可验证的细节(`register()` 返回处置器)。
- **祈使或陈述,不留余地。** 用「必须」「绝不」,不用「建议」「尽量」。模态词一模糊,AI 就会自行权衡。
- **点名具体的 API、路径、检查。** 写 `ctx.effect()` 而不是「注册机制」;写 `verify-cordis-config` 而不是「相关门禁」。
- **不解释为什么。** 想知道为什么,顺着链接去决策记录里看。

再看一条带链接的:

> **Prefer maintained dependencies over hand-rolling** when they genuinely delete owned code and tests([政策](../.agents/notes/implemented/process/2026-07-26-dependencies-over-hand-rolling.md))。

结论 + 生效条件 + 一个链接。**链接不是装饰**:AI 碰到规则没覆盖的情况时,它是唯一能自己找到判断依据的入口。

## 三个不显然的取舍

### 它是索引,不是教程

每条规则一两行给结论,细节放在别处。

**好在哪。** 这个文件每个 session 都要塞进 AI 的上下文。写成教程它会膨胀到几千词,每次对话都在为这些字付费,而且真正要紧的几条被淹在里面。dsh 干脆给根文件设了约 1600 词的上限,用脚本卡住。

这条上限本身也有一篇决策记录:[doc-tiers-and-budgets](../.agents/notes/implemented/process/2026-07-04-doc-tiers-and-budgets.md)。它规定了超了之后的处理顺序 —— **先把内容搬到该去的地方,再压缩,最后才考虑抬上限**,而且抬上限要在 PR 里说明理由。

**这条记录的价值在于**:没有它,下一个人碰到门禁报红,最省事的做法就是把上限从 1600 改成 2000,门禁就此失效。有了它,改上限得先驳倒记录在案的顺序。

### 分层

根目录一份通用的,子目录各放一份该目录专属的,AI 在哪个目录干活就叠加哪一层。这个仓库里有六份,可以直接点开看:

| 文件 | 管什么 |
|---|---|
| [AGENTS.md](../AGENTS.zh.md) | 根:项目定位、目录地图、命令表、代码约定 |
| [docs/AGENTS.md](../docs/AGENTS.zh.md) | 文档:分层、一个事实一个家、字数预算 |
| [packages/AGENTS.md](../packages/AGENTS.zh.md) | 包:插件导出形式、服务设计、边界校验 |
| [scripts/AGENTS.md](../scripts/AGENTS.zh.md) | 脚本 |
| [.github/AGENTS.md](../.github/AGENTS.zh.md) | CI 与 PR |
| [.agents/notes/AGENTS.md](../.agents/notes/AGENTS.zh.md) | 决策记录 |

**好在哪。** 拿 [packages/AGENTS.md](../packages/AGENTS.zh.md) 举例,它开头第一条就是:

> **Plugin exports:** service packages default-export their service class; function plugins named-export `name` / `inject` / `Config` / `apply` and have no default export.

这条只在写包的时候有意义,写文档的人不需要知道。如果所有规则都堆在根文件里,根文件会有几百条,而且每个 session 无论干什么都要读全部。分层之后,改文档的 AI 读到的是文档规则,改包的读到的是包规则。

顺带一提,这条规则后面挂的链接指向一篇事故复盘 —— 混用两种导出形式会让 Loader 静默丢弃插件的命名空间。规则是从踩过的坑里长出来的,不是凭空定的。

### 子树那一份只写差异

子目录的 `AGENTS.md` 开头一句就说明自己是补充,比如 [packages/AGENTS.md](../packages/AGENTS.zh.md) 写的是「以下是针对包的规则,是对仓库全局约定的补充」。

**好在哪。** 它不重复根文件已有的内容。同一条规则出现在两处,改的时候必然漏一处,然后两份说法就开始冲突 —— AI 读到冲突的规则,行为不可预测。

## 搬到自己项目

1. 仓库根建 `AGENTS.md`,`ln -s AGENTS.md CLAUDE.md`。
2. 先只写开篇、命令、约定三节。约定那节从你**最反复交代**的五六条开始。
3. 给它设一个字数上限,写进 CI(见[第三篇](03-gates.md))。
4. 等某个子目录的特殊规矩攒到三条以上,再给那个目录单开一份,并且只写差异。

## 容易做错的地方

**不要写成教程,要只留结论加链接。** 一膨胀就没人读,包括 AI —— 它会读,但重点被淹了。判断标准:一条规则超过三行,就把详情搬走、留个链接。

**不要只写「做什么」,要同时留下「为什么」的入口。** 只有做法的规则,AI 照着做没问题,但碰到规则没覆盖的情况就只能瞎猜。每条挂一个链接的成本很低。

**不要用「建议」「尽量」这类软措辞,要用「必须」「绝不」。** 模态词一模糊,AI 就会自行权衡,而它的权衡标准跟你的不一样。

**不要让规则和现实脱节,要把这份文件纳入同一次改动的检查范围。** 命令改了、目录挪了,`AGENTS.md` 没跟着改,AI 就会按过时的信息干活 —— 而且它不会怀疑。

**不要把同一条规则写在根文件和子树文件两处,要让子树那份只写差异。** 两处重复,改的时候必然漏一处,之后两份说法开始冲突。

# DeepSeek Harness Prose Standard(中文对照)

> 这是 [SKILL.md](SKILL.md) 的中文对照,供阅读方便。**英文原文是权威版本**,执行规则时以原文为准。
>
> 触发场景:在这个仓库里撰写、评审、恢复、精简或审计 prose 时用它,包括判定 Markdown、JSDoc、代码与测试注释、提示词、描述、诊断信息以及 CLI/UI 字符串里哪些地方必须有文档或注释。

写够以保住契约,然后去掉推理过程的记录、重复和装饰。契约指的是调用方、被调方、实现者、生产者或消费者所依赖的一项义务、不变量、前置条件、后置条件或兼容承诺。本 skill 负责编辑判断与必需的 prose 覆盖;放置位置、字数预算、双语对照与文档门禁用 [dsh-doc-standards](../dsh-doc-standards/SKILL.md),搜查并修复推理过程泄漏用 [dsh-trim-cot-leakage](../dsh-trim-cot-leakage/SKILL.md)。它是指南,不是脚本。

把 `contract`、`boundary`、`shape`、`surface`、`seam`、`gate`、`vocabulary` 当作「用之前先核对」的词,而不是禁用词。先问一句:确切的那条规则、API、字段集、类型、校验、时间点、组件划分或失败状态,是不是把这个事实说得更准。当这个词确实点名了那个确切的技术对象时就保留它 —— 包括调用方与被调方之间的契约,以及安全或进程边界。

注释描述的是代码无法表达的、不显然的契约或理由;它们不复述代码本身已经隐含的东西。

## 输入与排除项

必须有一个显式的 `scope`。如果缺,就报告这个必需输入并停下;不要推断出一个覆盖整个仓库的范围,也不要开始追问。

接受 `mode: automatic | interactive`;默认 `automatic`。只有用户显式要求提问或校准时才进入 interactive 模式。

`mode` 控制的是「是否提问」,不是「是否有写入权」。评审与审计类任务只报告发现、不编辑;被显式要求的写入、修复或精简类任务则实施明确的改动。

始终把 `vendor/` 从发现、评审与编辑中排除掉,即使请求的范围是整个仓库。不要顺着软链接进入它。把排除项放在包含类 glob 之后,这样后面的包含项不会又把它放进来:例如 ripgrep 命令末尾加 `--glob '!vendor/**'`,Git 命令给一个显式的 `:(exclude)vendor/**` pathspec。如果请求的范围里只有 `vendor/`,就报告没有符合条件的文件剩下。

同样把 `.agents/notes/archived/` 从 prose 评审与编辑中排除。归档的 Agent Note 是冻结的快照;只有为了理解一条历史上的入链引用,才去查看某个确切目标,绝不为了让它的 prose 或外链现代化而动它。

把生成的目录、快照和 fixture 当作派生物。先改拥有它的源文件或场景,再重新生成产物。当某个生成器从所有者的 prose 里抽取一段摘要时,要让被抽取的那句话在那个表面上是完整的。双语对照没有永久的所有者:任一语言都可以是本次改动的作者侧。走[轻量的常规路径](../../../docs/AGENTS.md#writing-rules),以最小改动更新对照页,然后重新记录这组配对。

## 保住完整的命题

编辑之前,先识别出这段话里的每一条命题。逐条保住其中相关的:

- 行为主体与动作;
- 条件、时序与先后顺序;
- 模态,例如必须(must)、可以(may)、绝不(never);
- 负向保证与例外;
- 所有权、副作用、失败模式与后果。

只有在每一条事实性子句都幸存、且结果更清楚的情况下,才去掉形容词、重复与叙述。**单是字数变少不算改进。**

在使用点上保留一份完整的本地契约:调用方或维护者在那里需要的行为、失败、所有权与后果。架构、理由、算法、历史或扩展示例,要积极地链到拥有它的那篇文档。一个解释只有一个家;必要的契约事实可以在本地重复。

当省略某条不显然的理由,有可能导致误用或错误的简化时,保留它。否则就陈述后果,并把理由链到它的家。

## 按 prose 所在位置的必需覆盖

这不是一趟单向的缩短作业。当代码、类型和结构没能传达下面某条必需的契约时,要新增或恢复 prose。而当这些事实在本地已经显然时,不要再加注释。

- **公开 JSDoc:** 记录调用方可见的返回值区分、抛出或 reject、副作用、所有权、时序、取消,以及持久性。
- **内部注释:** 为非局部的结构以及明显复杂的局部结构提供定位,包括不变量、竞态顺序、所有权、安全边界,以及出人意料的失败行为。删掉控制流叙述与对代码的复述。
- **模块注释:** 说明该模块的角色、依赖、职责,以及不显然的架构选择;把架构选择链到拥有其解释的地方。
- **测试:** 只解释不显然的测试设计 —— 为什么需要这个 fixture、这条断言、这处平台适配、这条真实入口路径或这种间接观察。删掉走查与清单。
- **cookbook:** 包含前置条件、必需的操作、真实的入口路径、可观察的验证,以及精简的警告。
- **README:** 包含消费者契约:配置、语义、失败、限制、扩展点,以及模型可见的效果。引用由该包拥有的稳定模型可见文本;链到生成的目录与跨包的所有者。保留持久存在的缺口与维护者陷阱,而不是普通的清理清单。遵循[包 README 的要求](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-a-package.md#4-write-the-package-readme)。
- **Agent Note:** 保住独有的理由、机制、备选方案、后果、已发布的验证证据,以及点名的覆盖缺口。已实现的 Agent Note 用现在时陈述已发布的现实;删掉计划清单,但不要删掉「什么钉住了这个决策」的证据。
- **事故复盘:** 保住事故顺序、证据、因果链、影响与预防措施。删掉重复的说服性文字,以及不构成因果关系的实现细节。
- **skill 与 agent 指令:** 陈述行为护栏和显式的范围限制,例如「指南,不是脚本/清单」。工作流保持精简,并链到它的权威来源。
- **示例与配置注释:** 解释访问限制、不显然的接线或加载顺序、安全立场、replay 行为、例外,以及可能的误用。不要叙述配置本身已经显示出来的条目。
- **提示词与可见字符串:** 把措辞当作行为。检查生成出的输出,并跑行为验证,或者说明为什么没有快照适用。
- **诊断信息:** 点名出错的对象或路径、被违反的规则,以及(在不显然时)如何纠正。删掉内部执行过程的叙述。

保住可搜索的机制名称,以及有意义的模态、时间或否定强调。只对装饰性的强调做归一化。

## 工作流

1. 确认范围、模式、当前分支或 PR 的 base,以及适用的 `AGENTS.md` 文件。不要去查看无关的分支。
2. 在判断一段话之前,先读[文档标准](../../../docs/AGENTS.md)以及拥有它的代码或文档。需要校准或遇到不熟悉的情况时,读[提炼出的示例](references/examples.md)。
3. 检查请求的整个范围,而不只是最大的那几个文件。用搜索和字数统计找出候选,然后对每段话做语义判断。
4. 把每个候选分类为:保留、新增、精简、恢复、重组或推迟。只有任务授权了编辑时才实施明确的改动;不要为了满足某个删减指标而制造编辑。
5. 先更新所有者,再更新派生产物。学到一条新规则之后,回头重新检查同类的段落。
6. 跑相关的窄检查、文档门禁、`git diff --check`,以及可见字符串的行为测试。核实最终 diff 里不含任何 `vendor/` 路径,并且如果意外命中了 vendor 就报告出来,而不是宣称排除历史干净。
7. 报告:检查过的范围、明确的改动、有意保留的地方、推迟的情况,以及实际跑过的检查。

## 边界情形的判断

只有当至少两个版本都满足「完整命题」规则、却在已被接受的原则之间做出取舍,并且本 skill 尚未裁定这个取舍时,才算边界情形。一次改写只有一个「保住命题」的答案,那就不是边界情形。

在 automatic 模式下,在被授权时实施明确的编辑,并报告真正的边界情形,不提问。**不要为了推进而弱化一条命题。**

在 interactive 模式下,把同类的段落按支配它们的原则归组。给出两到三个可行版本,推荐其中一个,并说明它们之间事实性或结构性的差别。不要提供明显更差的干扰项。使用用户要求的渠道;当通过行内评论对一个 PR 做校准时,把推荐的临时版本放进 diff,并把备选方案挂在那一行上。

用户做出决定之后,把这条原则与那些版本提炼进[示例集](references/examples.md),不带 PR 历史与评审者叙述,并把学到的规则应用到范围内每一段同类的话上。
